# Phase 9.6: Query Cache Integration

## Overview

Query Cache Integration connects the natural language query planner (Phase 9.5) with the multi-level cache system (Phase 13) to provide intelligent caching of query plans and results. This integration reduces latency for repeated queries, optimizes resource usage through cache warming, and maintains consistency through intelligent invalidation.

### Core Objectives

1. **Plan Caching**: Cache generated query plans to avoid redundant planning overhead
2. **Result Caching**: Cache query results using the L3 query cache infrastructure
3. **Cache Key Generation**: Generate efficient cache keys from natural language queries
4. **Cache Warming**: Pre-populate cache based on access patterns and predictions
5. **Intelligent Invalidation**: Invalidate cached data when underlying entities change
6. **Adaptive Sizing**: Adjust cache sizes based on usage patterns and performance metrics
7. **Statistics Collection**: Track cache effectiveness with detailed metrics

### Integration Points

- **Consumes**: Natural language queries from users
- **Uses**: QueryPlanner from Phase 9.5 for plan generation
- **Uses**: L3 QueryCache from Phase 13 for result storage
- **Uses**: Entity/Topic/Relationship cartridges from Phase 9.4
- **Produces**: Cached query plans and results
- **Invalidates**: On commit mutations and cartridge updates

## Natural Language Description

### Query Cache Integration Flow

The query cache integration sits between the user's natural language query and the database execution, providing transparent caching at multiple levels:

```
User Query: "Show all functions modified by nikos in the storage layer"
    ↓
1. Cache Key Generation
   - Normalize query: lowercase, trim whitespace
   - Extract entities: [nikos, storage layer]
   - Generate hash: SHA-256(query + entities)
   - Create composite key: (hash, snapshot_lsn)
    ↓
2. Plan Cache Lookup
   - Check if query plan exists for this key
   - If hit: Reuse cached plan (skip LLM call)
   - If miss: Generate plan using QueryPlanner
    ↓
3. Result Cache Lookup
   - Check if query result exists for this key
   - If hit: Return cached result immediately
   - If miss: Execute query using plan
    ↓
4. Cache Population
   - Store generated plan in plan cache
   - Store executed result in result cache
   - Track page dependencies for invalidation
    ↓
5. Return Result to User
```

### Multi-Level Caching Strategy

The integration uses three complementary caching levels:

1. **Plan Cache (L0)**: Stores QueryPlan objects to avoid redundant LLM calls
   - Key: (normalized_query_hash, entity_refs_hash)
   - Value: Complete QueryPlan with operations and hints
   - TTL: 1 hour (plans are stable)
   - Size: 10,000 plans (approximately 50MB)

2. **Result Cache (L1)**: Uses existing L3 QueryCache for query results
   - Key: (plan_hash, snapshot_lsn)
   - Value: QueryResult with page dependencies
   - TTL: 5 seconds (results are time-sensitive)
   - Size: 32MB (configured in QueryCache)

3. **Entity Cache (L2)**: Implicit caching through cartridge lookups
   - EntityCartridge get_by_name/id lookups
   - TopicCartridge keyword searches
   - RelationshipCartridge traversal results

## Cache Key Generation

### Natural Language Normalization

Before generating cache keys, normalize the query to ensure consistent hashing:

1. **Case Normalization**: Convert to lowercase
2. **Whitespace Normalization**: Collapse multiple spaces to single space
3. **Punctuation Handling**: Remove unnecessary punctuation (keep quotes for literals)
4. **Entity Extraction**: Extract and sort entity references

Example normalization:
- Input: "  Show  ALL  functions  by  NIKOS  in  'Storage'  layer  "
- Output: "show all functions by nikos in 'storage' layer"
- Entities: ["nikos", "storage layer"]

### Query Plan Key Structure

The plan cache key uniquely identifies a query pattern independent of snapshot:

```
struct QueryPlanKey {
    // Hash of normalized query text
    normalized_query_hash: u64,  // SipHash-2-4 of normalized text

    // Hash of extracted entity references
    entity_refs_hash: u64,  // SipHash-2-4 of sorted entity list

    // Query intent type
    intent_type: QueryIntent,  // PointLookup, SemanticSearch, etc.

    // Snapshot-independent identifier
    // (different snapshots can reuse the same plan)
}
```

**Key Generation Algorithm**:

1. Normalize the query text (lowercase, trim, collapse whitespace)
2. Extract entity references using entity linker
3. Sort entity references alphabetically for consistency
4. Hash normalized query using SipHash-2-4 with fixed key
5. Hash sorted entity list using SipHash-2-4 with fixed key
6. Classify query intent (lightweight keyword matching)
7. Combine into composite key

**Example**:

```
Query: "Show all commits by nikos"
Normalized: "show all commits by nikos"
Entities: ["nikos"]
Intent: SemanticSearch

normalized_query_hash: 0x8f3a2b1c4d5e6f7a
entity_refs_hash: 0x1a2b3c4d5e6f7890
intent_type: SemanticSearch

QueryPlanKey: {
    normalized_query_hash: 0x8f3a2b1c4d5e6f7a,
    entity_refs_hash: 0x1a2b3c4d5e6f7890,
    intent_type: SemanticSearch
}
```

### Query Result Key Structure

The result cache key includes snapshot information for MVCC correctness:

```
struct QueryResultKey {
    // Hash of the query plan (execution fingerprint)
    plan_hash: u64,

    // Snapshot LSN (for MVCC correctness)
    snapshot_lsn: Lsn,

    // Query parameters that affect results
    // (limits, offsets, sort orders, etc.)
    params_hash: u64,
}
```

**Key Generation Algorithm**:

1. Generate or retrieve query plan
2. Hash the plan structure (operations, entity links)
3. Include snapshot LSN in key
4. Hash query parameters (limit, offset, sort direction)
5. Combine into composite result key

**MVCC Correctness**:

Different snapshots must see different cached results even for identical queries. The snapshot_lsn in the key ensures:
- Snapshot at LSN 100 queries: cache miss → execute → store in cache
- Snapshot at LSN 150 queries: cache miss (different LSN) → execute → store
- Snapshot at LSN 100 again: cache hit (same key as first query)

## Cache Warming Strategies

### Query Frequency Tracking

Track which queries are executed most frequently to prioritize warming:

```
struct QueryFrequency {
    // Query plan key
    plan_key: QueryPlanKey,

    // Execution count
    count: u64,

    // Last execution timestamp
    last_executed: SystemTime,

    // Average execution time
    avg_latency_ms: f64,

    // Cache hit rate
    hit_rate: f64,
}
```

**Frequency Tracking Algorithm**:

1. Maintain frequency table in memory (max 10,000 entries)
2. Increment count on each query execution
3. Update last_executed timestamp
4. Calculate exponential moving average of latency
5. Track hit rate separately
6. Evict least-recently-used entries when table is full

### Pattern-Based Warming

Identify access patterns and pre-warm likely queries:

**Time-Based Patterns**:
- Morning queries: "show commits since yesterday"
- End-of-week queries: "show summary for this week"
- Start-of-month queries: "show metrics for last month"

**Entity-Based Patterns**:
- After commit on file X: pre-warm queries for X
- After entity lookup for person Y: pre-warm Y's relationships
- After topic access: pre-warm related topics

**Session-Based Patterns**:
- First query in session: warm common queries
- Repeated entity references: warm related entity queries
- Semantic queries: warm follow-up refinements

### LLM-Predicted Warming

Use the LLM to predict likely follow-up queries:

**Prediction Algorithm**:

1. Analyze current query context
2. Call LLM with "suggest_followup_queries" function
3. Pre-execute top N predicted queries in background
4. Store results in cache
5. Serve immediately if user executes them

**Example**:

```
Current Query: "show commits by nikos"
LLM Predictions:
  1. "show commits by nikos in the last week" (confidence: 0.9)
  2. "show files modified by nikos" (confidence: 0.8)
  3. "show commits related to storage by nikos" (confidence: 0.7)

Pre-warm: Execute top 2 predictions in background, cache results
```

**LLM Function Schema**:

```json
{
  "name": "suggest_followup_queries",
  "description": "Suggest likely follow-up queries based on current query context",
  "parameters": {
    "type": "object",
    "properties": {
      "current_query": {
        "type": "string",
        "description": "The current query being executed"
      },
      "recent_queries": {
        "type": "array",
        "items": {"type": "string"},
        "description": "Recent queries in this session"
      },
      "suggestions": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "query": {"type": "string"},
            "confidence": {"type": "number"}
          }
        }
      }
    }
  }
}
```

## Cache Invalidation

### Invalidation on Commits

When a WriteTxn commits, invalidate affected cache entries:

```
struct CommitInvalidation {
    // Transaction ID
    txn_id: TransactionId,

    // Committed LSN
    commit_lsn: Lsn,

    // Mutations performed
    mutations: Vec<Mutation>,

    // Affected entity IDs
    affected_entities: Vec<String>,

    // Affected pages
    affected_pages: Vec<PageId>,
}
```

**Invalidation Algorithm**:

1. **Extract Affected Entities**:
   - From mutations: extract entity IDs being modified
   - From page dependencies: map pages to entity IDs
   - Build set of affected entity IDs

2. **Invalidate Query Plans**:
   - Scan plan cache for plans referencing affected entities
   - Remove plans that depend on modified entities
   - Keep plans for unrelated entities

3. **Invalidate Query Results**:
   - Use existing page-based invalidation from QueryCache
   - Invalidate results depending on modified pages
   - Track invalidation count for metrics

4. **Update Statistics**:
   - Increment invalidation counters
   - Update cache hit/miss rates
   - Log for monitoring

**Example**:

```
Commit: Insert new FunctionEntity "northstar_db::init"
Affected Entities: ["function:northstar_db::init", "topic:database"]
Affected Pages: [1234, 5678]

Plan Cache Invalidation:
  - Remove: "get function northstar_db::init" (references function:northstar_db::init)
  - Remove: "show database functions" (references topic:database)
  - Keep: "show storage layer functions" (different topic)

Result Cache Invalidation:
  - QueryCache.invalidate(pages [1234, 5678])
  - Removes 3 cached results depending on those pages
```

### Time-Based Expiration

In addition to commit-based invalidation, use TTL expiration:

**Plan Cache TTL**: 1 hour
- Plans are stable but entity references may change
- Long TTL allows reuse across many queries
- Invalidation on entity cartridge updates

**Result Cache TTL**: 5 seconds (configurable)
- Results are time-sensitive (new commits may change data)
- Short TTL ensures freshness
- Can be overridden per-query if needed

**TTL Adjustment**:
- Stable queries (historical data): longer TTL (60 seconds)
- Real-time queries (current state): shorter TTL (1 second)
- User-specified: explicit TTL parameter

### Manual Invalidation

Support explicit cache clearing operations:

```
// Clear all caches
query_cache.clear_all();

// Clear specific entity
query_cache.clear_entity("entity:123");

// Clear specific pattern
query_cache.clear_pattern("show commits by *");

// Clear expired entries
query_cache.clear_expired();
```

## Adaptive Cache Sizing

### Dynamic Sizing Algorithm

Adjust cache sizes based on usage patterns:

**Plan Cache Sizing**:

1. Monitor plan cache hit rate over time window (5 minutes)
2. If hit rate > 80% and evictions = 0: reduce size by 10%
3. If hit rate < 60% or evictions > 100: increase size by 20%
4. Clamp size between min (1,000 plans) and max (50,000 plans)
5. Resize cache and migrate hot entries

**Result Cache Sizing**:

1. Monitor result cache hit rate and memory usage
2. If hit rate > 70% and memory < 80%: increase size by 10%
3. If hit rate < 50% or memory > 90%: decrease size by 10%
4. Clamp size between min (8MB) and max (128MB)
5. Adjust TTL proportionally to size

**Memory Pressure Handling**:

When system memory is constrained:

1. Reduce result cache size first (results are cheaper to recompute)
2. Reduce plan cache size if still under pressure
3. Increase eviction rate
4. Shorten TTL to reduce retention
5. Log warnings for monitoring

### Cache Priority System

Prioritize which entries to keep during pressure:

```
enum CachePriority {
    High,      // Frequently used, low recomputation cost
    Medium,    // Moderate use, moderate cost
    Low,       // Rarely used, high recomputation cost
}

struct CacheEntry<T> {
    value: T,
    priority: CachePriority,
    frequency: u64,
    last_access: SystemTime,
    recomputation_cost: f64,  // Estimated time to recompute
}
```

**Priority Assignment**:

- High: Query frequency > 100/hour, latency > 100ms
- Medium: Query frequency 10-100/hour, latency 10-100ms
- Low: Query frequency < 10/hour, latency < 10ms

**Eviction Order**:

1. Evict Low priority entries first
2. Then Medium priority entries
3. Keep High priority entries unless memory critical

## Integration with L1/L2/L3 Cache

### Cache Hierarchy

The query cache integration sits atop the existing cache hierarchy:

```
Level 0: Query Plan Cache (NEW)
  └─ Stores: QueryPlan objects
  └─ Key: (query_hash, entity_hash)
  └─ TTL: 1 hour
  └─ Size: 10,000 entries (~50MB)

Level 1: Query Result Cache (L3 - Existing)
  └─ Stores: QueryResult objects
  └─ Key: (plan_hash, snapshot_lsn)
  └─ TTL: 5 seconds
  └─ Size: 32MB

Level 2: Node Cache (L2 - Existing)
  └─ Stores: B+Tree internal nodes
  └─ Key: NodeId
  └─ Policy: LRU
  └─ Size: 16MB

Level 3: Page Cache (L1 - Existing)
  └─ Stores: 16KB disk pages
  └─ Key: PageId
  └─ Policy: LRU/LFU/ARC
  └─ Size: 256MB
```

### Query Execution Flow with Caching

```
1. User Query: "show commits by nikos"
   ↓
2. Plan Cache Lookup (Level 0)
   - Hit: Reuse plan → skip LLM call (~200ms saved)
   - Miss: Generate plan using QueryPlanner
   ↓
3. Result Cache Lookup (Level 1)
   - Hit: Return result immediately (~1ms)
   - Miss: Continue to execution
   ↓
4. Execute Query Plan
   - Use Node Cache (Level 2) for tree traversal
   - Use Page Cache (Level 3) for page reads
   ↓
5. Store Result in Level 1 Cache
   - Track page dependencies for invalidation
   ↓
6. Return Result to User
```

### Cross-Level Invalidation

Invalidation propagates through cache levels:

```
WriteTxn Commit on Page 1234:
    ↓
1. L3 Page Cache
   - Invalidate page 1234
    ↓
2. L2 Node Cache
   - Invalidate nodes containing page 1234
    ↓
3. L1 Query Result Cache
   - Invalidate results with page_dependencies containing 1234
    ↓
4. L0 Query Plan Cache
   - Invalidate plans that reference affected entities
   - Keep plans if only pages changed (structure same)
```

## Performance Targets

### Cache Effectiveness

1. **Plan Cache Hit Rate**: > 60% for repeated queries
   - Typical workloads have repeated query patterns
   - Saves LLM overhead (200-500ms per query)

2. **Result Cache Hit Rate**: > 40% for repeated queries
   - Short TTL limits hit rate
   - Still significant savings for hot queries

3. **Overall Latency Reduction**: > 50% for cached queries
   - Plan cache hit: save ~200ms (LLM call)
   - Result cache hit: save ~100ms (execution)

4. **Memory Overhead**: < 100MB total
   - Plan cache: ~50MB
   - Result cache: ~32MB
   - Metadata and statistics: ~18MB

### Query Latency Breakdown

**Uncached Query**:
- Intent classification: 50ms (LLM)
- Entity extraction: 100ms (LLM)
- Query planning: 50ms (optimization)
- Query execution: 100ms (tree operations)
- **Total: ~300ms**

**Plan Cache Hit**:
- Plan lookup: 1ms
- Query execution: 100ms
- **Total: ~101ms (66% reduction)**

**Result Cache Hit**:
- Result lookup: 1ms
- **Total: ~1ms (99% reduction)**

### Test Scenarios

**Scenario 1: Repeated Query**

```
1. Execute: "show commits by nikos"
   - Plan cache: miss (generate plan)
   - Result cache: miss (execute query)
   - Store both in cache

2. Execute: "show commits by nikos" (same snapshot)
   - Plan cache: hit (reuse plan)
   - Result cache: hit (reuse result)
   - Return immediately

3. Execute: "show commits by nikos" (different snapshot)
   - Plan cache: hit (reuse plan)
   - Result cache: miss (different LSN)
   - Execute query, store result
```

**Scenario 2: Commit Invalidation**

```
1. Execute: "show commits by nikos"
   - Cache result with page dependencies [123, 456]

2. Commit new commit by nikos
   - Modifies pages [123, 456]
   - Trigger invalidation

3. Execute: "show commits by nikos" (same snapshot)
   - Plan cache: hit (plan still valid)
   - Result cache: miss (invalidated by commit)
   - Execute query, store new result
```

**Scenario 3: Cache Warming**

```
1. Execute: "show commits by nikos"
   - Track query frequency
   - Identify as high-frequency query

2. System detects warming opportunity
   - Predict: "show commits by nikos in storage layer"
   - Pre-execute in background
   - Store result in cache

3. User executes: "show commits by nikos in storage layer"
   - Result cache: hit (pre-warmed)
   - Return immediately
```
