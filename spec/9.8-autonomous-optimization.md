# Phase 9.8: Autonomous Optimization Manager

## Overview

Autonomous Optimization Manager is the capstone of the AI Intelligence Layer, enabling NorthstarDB to self-optimize based on usage patterns, performance metrics, and resource availability. This system automatically creates indexes, warms caches, optimizes cache sizing, archives cold data, compacts storage, and schedules maintenance - all while maintaining safety constraints and rollback capabilities.

### Core Objectives

1. **Autonomous Index Management**: Automatically create, modify, and drop indexes based on query patterns
2. **Intelligent Cache Warming**: Pre-load hot keys and frequent queries into cache
3. **Dynamic Cache Sizing**: Automatically adjust cache sizes based on hit rates and memory pressure
4. **Data Archival**: Move cold data to cloud storage based on access patterns
5. **Storage Compaction**: Automatically vacuum and compact database files
6. **Query Plan Optimization**: Automatically optimize query execution plans
7. **Maintenance Scheduling**: Schedule optimizations during low-traffic windows
8. **Safety and Rollback**: Dry-run mode, approval workflows, automatic rollback on regression

### Integration Points

- **Consumes**: UsageAnalytics from Phase 9.7 (patterns, hot keys, cold data, recommendations)
- **Consumes**: QueryCache from Phase 9.6 (for warming and sizing)
- **Consumes**: Monitoring metrics (CPU, memory, disk, performance)
- **Modifies**: B+tree indexes (create/drop)
- **Modifies**: Cache configuration (size, warming)
- **Uses**: Cloud storage adapters from Phase 16 (archival)
- **Emits**: AutonomousOptimization events (started, completed, rolled back)

### Optimization Types

#### 1. Index Creation

**When to Create**:
- High-frequency point lookups without index (> 1000 executions/hour)
- Range scans on non-indexed columns with high selectivity
- Join predicates without indexes
- ORDER BY/GROUP BY on non-indexed columns

**Creation Process**:
1. **Candidate Identification**:
   - Analyze query patterns from UsageAnalytics
   - Find columns frequently used in WHERE clauses
   - Check if index exists on column
   - Estimate index size and build time

2. **Impact Estimation**:
   - Calculate expected latency reduction (80-95% for point lookups)
   - Calculate storage overhead (index size)
   - Calculate write overhead (index maintenance)
   - Estimate build time (proportional to table size)

3. **Safety Checks**:
   - Available storage > 2x estimated index size
   - Write capacity budget > 10% for index maintenance
   - Not in maintenance window restriction period
   - Dry-run mode: simulate index creation

4. **Execution**:
   - Create index with CONCURRENT option (non-blocking)
   - Monitor build progress
   - Validate index correctness
   - Update query planner statistics

5. **Validation**:
   - Measure query latency after index creation
   - Verify latency reduction within 20% of estimate
   - Monitor write throughput impact
   - Rollback if regression detected

**Example**:
```
Pattern: Full scans on users table (age column)
- Execution count: 10,000 queries
- Avg latency: 250ms
- Scan/return ratio: 1000 (inefficient)

Recommendation: Create index on users.age
- Estimated latency reduction: 90%
- Storage overhead: 50MB
- Build time: 5 minutes
- Effort: Low
- Priority: High

Execution:
1. Check available storage: 2GB OK
2. Check maintenance window: 2-4 AM OK
3. Create index CONCURRENTLY
4. Monitor: Build progress 20%... 40%... 100%
5. Validate: Query latency now 25ms (90% reduction)
6. Commit optimization
```

#### 2. Cache Warming

**When to Warm**:
- Top 100 hot keys by access frequency
- Frequent queries with high latency
- Predictable access patterns (time-based)

**Warming Process**:
1. **Candidate Identification**:
   - Get top K hot keys from UsageAnalytics
   - Get frequent queries from pattern registry
   - Filter by hotness score > 0.7

2. **Cache Selection**:
   - Read hot keys → L1 page cache
   - Hot spots → L2 node cache
   - Frequent queries → Query result cache

3. **Execution**:
   - Batch load keys into cache
   - Pre-execute frequent queries
   - Pin warmed entries in cache

4. **Validation**:
   - Monitor cache hit rate
   - Verify latency reduction
   - Unpin if not accessed after 1 hour

**Example**:
```
Hot Key: user:1234
- Read frequency: 1000/sec
- Hotness score: 0.95
- Avg read latency: 50ms (cold cache)
- Expected warmed latency: 1ms

Action: Pre-load user:1234 into L1 cache
1. Load key from disk
2. Pin in L1 cache
3. Monitor: Next 100 reads hit cache (100% hit rate)
4. Result: 98% latency reduction (50ms → 1ms)
```

#### 3. Cache Sizing

**When to Resize**:
- Cache hit rate < 70% for > 1 hour (increase cache)
- Cache hit rate > 95% with memory pressure (decrease cache)
- Memory utilization > 90% (decrease cache)
- Available memory > 50% (increase cache)

**Sizing Process**:
1. **Analysis**:
   - Calculate current hit rate (EMA over last hour)
   - Calculate miss penalty (avg cost of cache miss)
   - Calculate memory value (hit_rate / memory_size)
   - Calculate optimal size (diminishing returns point)

2. **Resize Calculation**:
   - Target hit rate: 80-90%
   - Calculate required size for target
   - Check available memory
   - Apply safety margin (20% buffer)

3. **Execution**:
   - Adjust cache configuration
   - No cache invalidation on size increase
   - LRU eviction on size decrease
   - Update monitoring metrics

4. **Validation**:
   - Monitor hit rate for next hour
   - Verify memory utilization within limits
   - Revert if hit rate degrades

**Example**:
```
Current State:
- L1 cache size: 100MB
- Hit rate: 65% (below target)
- Miss penalty: 10ms per miss
- Memory available: 2GB

Analysis:
- Current hit rate 65% too low
- Increasing to 200MB should achieve 85% hit rate
- Cost: 100MB additional memory
- Benefit: 20% more hits = 2ms latency reduction

Action: Increase L1 cache to 200MB
1. Resize cache (non-blocking)
2. Monitor hit rate: 65% → 82% over next hour
3. Validate: Memory usage 200MB + 20% buffer = 240MB OK
4. Commit new size
```

#### 4. Data Archival

**When to Archive**:
- Data not accessed in > 90 days
- Cold data classification from UsageAnalytics
- Large tables with low access rate

**Archival Process**:
1. **Candidate Identification**:
   - Query cold data registry
   - Filter by days_since_last_access > 90
   - Filter by estimated_size_bytes > 10MB
   - Check for foreign key references

2. **Archival Strategy**:
   - **Read-Only Archive**: Keep in DB, mark read-only
   - **S3 Standard**: Move to S3, keep metadata
   - **S3 Glacier**: Move to cold storage, retrieval delay
   - **Delete**: Safe to delete (no FK refs)

3. **Execution**:
   - Export data to cloud storage (Phase 16)
   - Create external table reference
   - Delete from local storage
   - Update statistics

4. **Validation**:
   - Verify export integrity
   - Test restoration process
   - Monitor cost savings

**Example**:
```
Cold Data: logs_2023 table
- Last access: 180 days ago
- Size: 5GB
- Access rate: 0.01 queries/day
- Recommendation: Archive to S3 Glacier

Action:
1. Export to S3 Glacier (cost: $0.004/GB/month = $0.02/month)
2. Create external table reference
3. Drop from local storage
4. Result: 5GB local storage freed
5. Cost savings: $1.00/month (EBS vs S3 Glacier)
```

#### 5. Storage Compaction

**When to Compact**:
- Page fragmentation > 30%
- Free pages > 20% of total pages
- Scheduled weekly maintenance

**Compaction Process**:
1. **Analysis**:
   - Scan page allocation bitmap
   - Calculate fragmentation ratio
   - Estimate compaction time

2. **Execution**:
   - Schedule during maintenance window
   - VACUUM FULL (rewrite table)
   - Rebuild indexes
   - Update statistics

3. **Validation**:
   - Verify fragmentation reduced
   - Verify no data loss
   - Measure performance improvement

**Example**:
```
Current State:
- Database size: 10GB
- Free pages: 3GB (30%)
- Fragmentation: 40%

Action: Vacuum and compact
1. Schedule: 3-4 AM maintenance window
2. Execute: VACUUM FULL
3. Result: Database size 7GB (3GB freed)
4. Fragmentation: 5%
5. Performance: 15% latency reduction (less I/O)
```

### Optimization Policy Engine

The policy engine evaluates optimization candidates using rules-based and ML-based approaches:

#### Rules-Based Policies

```rust
struct OptimizationPolicy {
    /// Index creation policy
    index_policy: IndexPolicy,

    /// Cache warming policy
    cache_warming_policy: CacheWarmingPolicy,

    /// Cache sizing policy
    cache_sizing_policy: CacheSizingPolicy,

    /// Data archival policy
    archival_policy: ArchivalPolicy,

    /// Compaction policy
    compaction_policy: CompactionPolicy,
}

struct IndexPolicy {
    /// Minimum execution count for index consideration
    min_execution_count: u64,  // 1000

    /// Minimum scan/return ratio for index recommendation
    min_scan_return_ratio: f64,  // 10.0

    /// Maximum index size as percentage of table size
    max_index_size_ratio: f64,  // 0.5

    /// Write overhead threshold (refuse if > 20%)
    max_write_overhead: f64,  // 0.2
}

impl OptimizationPolicy {
    fn evaluate_index_candidate(&self, pattern: &QueryPattern) -> Option<IndexCandidate> {
        // Rule 1: Must have sufficient execution frequency
        if pattern.execution_count < self.index_policy.min_execution_count {
            return None;
        }

        // Rule 2: Must be inefficient (high scan/return ratio)
        if pattern.scan_return_ratio < self.index_policy.min_scan_return_ratio {
            return None;
        }

        // Rule 3: Estimated benefit must exceed cost
        let estimated_benefit = self.estimate_index_benefit(pattern);
        let estimated_cost = self.estimate_index_cost(pattern);

        if estimated_benefit < estimated_cost * 2.0 {
            return None;  // Benefit must be at least 2x cost
        }

        Some(IndexCandidate {
            table_name: pattern.table_name.clone(),
            columns: pattern.columns_accessed.clone(),
            estimated_benefit,
            estimated_cost,
            confidence: 0.85,
        })
    }
}
```

### Maintenance Window Scheduler

Optimizations are scheduled during low-traffic periods to minimize impact:

```rust
struct MaintenanceScheduler {
    /// Maintenance windows [start_hour, end_hour]
    windows: Vec<(u8, u8)>,  // [(2, 4), (14, 15)]  // 2-4 AM, 2-3 PM

    /// Current load threshold (abort if load > threshold)
    max_load_threshold: f64,  // 0.3 (30% CPU)

    /// Emergency optimizations (bypass maintenance window)
    emergency_mode: bool,
}

impl MaintenanceScheduler {
    fn can_execute_now(&self, optimization: &Optimization) -> bool {
        // Emergency optimizations always allowed
        if self.emergency_mode && optimization.is_emergency() {
            return true;
        }

        // Check if within maintenance window
        if !self.is_in_maintenance_window() {
            return false;
        }

        // Check current load
        if self.current_load() > self.max_load_threshold {
            return false;
        }

        true
    }

    fn schedule_optimization(&self, optimization: Optimization) -> ScheduledTime {
        if self.can_execute_now(&optimization) {
            ScheduledTime::Now
        } else {
            let next_window = self.next_maintenance_window();
            ScheduledTime::At(next_window)
        }
    }
}
```

### Safety Constraints and Rollback

#### Safety Mechanisms

1. **Dry-Run Mode**:
   - Simulate optimizations without applying
   - Generate estimated impact report
   - Validate safety constraints

2. **Approval Workflow**:
   - Low-risk optimizations: Auto-approve
   - Medium-risk optimizations: Log and notify
   - High-risk optimizations: Require manual approval

3. **Impact Estimation**:
   - Latency impact: ±10% tolerance
   - Throughput impact: ±10% tolerance
   - Storage impact: ±20% tolerance

4. **Resource Limits**:
   - Max optimization time: 1 hour
   - Max storage overhead: 10% of DB size
   - Max CPU usage: 50% during optimization

#### Rollback Mechanism

```rust
struct RollbackManager {
    /// Optimization history for rollback
    history: BTreeMap<OptimizationId, OptimizationRecord>,
}

struct OptimizationRecord {
    /// Optimization ID
    id: OptimizationId,

    /// Optimization type
    optimization_type: OptimizationType,

    /// Pre-optimization state
    before_state: SystemState,

    /// Post-optimization state
    after_state: SystemState,

    /// Rollback function
    rollback_fn: Box<dyn Fn() -> Result<()>>,
}

impl RollbackManager {
    fn rollback(&self, id: OptimizationId) -> Result<()> {
        let record = self.history.get(&id)
            .ok_or(Error::OptimizationNotFound)?;

        // Execute rollback function
        (record.rollback_fn)()?;

        // Restore pre-optimization state
        self.restore_state(&record.before_state)?;

        Ok(())
    }

    fn auto_rollback_if_needed(&self, id: OptimizationId) -> Result<bool> {
        let record = self.history.get(&id)
            .ok_or(Error::OptimizationNotFound)?;

        // Check for performance regression
        let current_latency = self.measure_current_latency();
        let baseline_latency = record.before_state.avg_latency;

        if current_latency > baseline_latency * 1.10 {
            // Regression detected (> 10%)
            self.rollback(id)?;
            return Ok(true);
        }

        Ok(false)
    }
}
```

### Autonomous Manager API

```rust
pub struct AutonomousManager {
    /// Policy engine
    policy: PolicyEngine,

    /// Usage analytics
    usage_analytics: Arc<UsageAnalytics>,

    /// Query cache
    query_cache: Arc<QueryCache>,

    /// Entity cartridge (for context)
    entity_cartridge: Arc<EntityCartridge>,

    /// Maintenance scheduler
    scheduler: MaintenanceScheduler,

    /// Rollback manager
    rollback: RollbackManager,

    /// Dry-run mode
    dry_run: bool,

    /// Approval mode
    approval_mode: ApprovalMode,
}

impl AutonomousManager {
    /// Run a full optimization cycle.
    pub async fn run_optimization_cycle(&mut self) -> Result<OptimizationReport> {
        // 1. Collect analytics
        let patterns = self.usage_analytics.get_query_patterns().await?;
        let hot_keys = self.usage_analytics.get_hot_keys().await?;
        let cold_data = self.usage_analytics.get_cold_data().await?;

        // 2. Generate candidates
        let mut candidates = Vec::new();

        // Index candidates
        for pattern in patterns {
            if let Some(candidate) = self.policy.evaluate_index_candidate(&pattern) {
                candidates.push(OptimizationCandidate::Index(candidate));
            }
        }

        // Cache warming candidates
        for hot_key in hot_keys {
            if let Some(candidate) = self.policy.evaluate_cache_warming(&hot_key) {
                candidates.push(OptimizationCandidate::CacheWarming(candidate));
            }
        }

        // Archival candidates
        for cold in cold_data {
            if let Some(candidate) = self.policy.evaluate_archival(&cold) {
                candidates.push(OptimizationCandidate::Archival(candidate));
            }
        }

        // 3. Filter and prioritize
        let candidates = self.filter_and_prioritize(candidates)?;

        // 4. Validate safety
        for candidate in &candidates {
            if !self.validate_safety(candidate).await? {
                continue;
            }
        }

        // 5. Execute optimizations
        let mut applied = Vec::new();
        for candidate in candidates {
            if self.dry_run {
                continue;
            }

            if let Some(result) = self.apply_optimization(&candidate).await? {
                applied.push(result);
            }
        }

        // 6. Generate report
        Ok(OptimizationReport {
            cycle_id: Uuid::new_v4(),
            started_at: SystemTime::now(),
            candidates_evaluated: candidates.len(),
            optimizations_applied: applied.len(),
            optimizations_skipped: candidates.len() - applied.len(),
            results: applied,
        })
    }

    /// Apply a specific optimization recommendation.
    pub async fn apply_recommendation(&mut self, rec: Recommendation) -> Result<()> {
        let optimization = self.recommendation_to_optimization(rec)?;

        // Validate safety
        self.validate_safety(&optimization).await?;

        // Schedule execution
        let scheduled_time = self.scheduler.schedule_optimization(optimization.clone());

        match scheduled_time {
            ScheduledTime::Now => {
                self.apply_optimization(&optimization).await?;
            }
            ScheduledTime::At(time) => {
                // Queue for later execution
                self.queue_optimization(optimization, time)?;
            }
        }

        Ok(())
    }

    /// Rollback a specific optimization.
    pub async fn rollback_optimization(&mut self, id: OptimizationId) -> Result<()> {
        self.rollback.rollback(id)?;
        self.emit_rollback_event(id)?;
        Ok(())
    }
}
```

## Performance Targets

### Optimization Overhead

1. **Analysis Overhead**: < 1% CPU
   - Pattern collection: < 100ms
   - Candidate generation: < 500ms
   - Safety validation: < 200ms
   - Total: < 1 second per cycle

2. **Execution Impact**: < 5% latency impact
   - Index creation: CONCURRENT option, non-blocking
   - Cache warming: Background threads, low priority
   - Cache resizing: Incremental, no cache flush
   - Archival: Background export, non-blocking

3. **Memory Overhead**: < 50MB
   - Policy engine: ~10MB
   - Optimization queue: ~10MB
   - Rollback history: ~20MB
   - Maintenance state: ~10MB

### Optimization Effectiveness

1. **Index Creation**:
   - Latency reduction: 80-95% for target queries
   - False positive rate: < 5% (indexes that don't help)
   - Storage overhead: < 50% of table size

2. **Cache Warming**:
   - Hit rate improvement: 20-40%
   - Latency reduction: 50-90% for warmed queries
   - Warm cache time: < 5 minutes for 1000 keys

3. **Cache Sizing**:
   - Hit rate target: 80-90%
   - Size adjustment accuracy: ±10%
   - Convergence time: < 2 hours

4. **Data Archival**:
   - Storage reduction: 30-70% for cold data
   - Cost reduction: 50-90% for cloud storage
   - Retrieval time: < 5 minutes for S3 Standard
