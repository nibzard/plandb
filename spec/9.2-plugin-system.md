# Plugin System v1 Specification

**Version**: 1.0
**Date**: 2026-01-05
**Status**: Draft
**Phase**: 9.2 - AI Intelligence Layer

## Overview

This specification defines the plugin system for NorthstarDB, enabling extensible AI intelligence through a lifecycle-based plugin architecture. The plugin system provides hooks into database events (commits, queries, scheduled tasks) while maintaining performance isolation and graceful degradation.

## Design Goals

1. **Event-Driven Architecture**: Plugins respond to database events through well-defined hooks
2. **Performance Isolation**: Plugin execution must not degrade core database performance
3. **Graceful Degradation**: Database remains functional even when plugins fail
4. **Resource Management**: Enforce quotas for memory, CPU, and execution time
5. **Type Safety**: Strong typing for all plugin operations and event data

## Plugin Lifecycle

### 1. Initialization (on_init)

Called when plugin is registered with the database.

**Context Provided**:
- Database configuration
- Plugin-specific configuration
- Access to event system
- Resource quota limits

**Responsibilities**:
- Validate configuration
- Initialize external connections (LLM providers, etc.)
- Register event subscriptions
- Allocate resources within quota

**Error Handling**:
- Initialization failure → plugin not registered
- Database continues without plugin
- Error logged for observability

### 2. Commit Hook (on_commit)

Called after each transaction commit.

**Event Data**:
```rust
pub struct CommitEvent {
    pub txn_id: TransactionId,
    pub lsn: Lsn,
    pub mutations: Vec<Mutation>,
    pub timestamp: i64,
    pub metadata: HashMap<String, String>,
}
```

**Typical Use Cases**:
- Extract entities and topics from mutations
- Update structured memory cartridges
- Analyze performance impact
- Trigger autonomous optimizations

**Execution Model**:
- Asynchronous (non-blocking)
- Timeout enforced (default: 5s)
- Error isolation (one plugin failure doesn't affect others)

### 3. Query Hook (on_query)

Called before query execution for optimization.

**Event Data**:
```rust
pub struct QueryEvent {
    pub query: String,
    pub query_type: QueryType,
    pub estimated_cost: f64,
    pub available_cartridges: Vec<CartridgeType>,
    pub constraints: QueryConstraints,
}

pub enum QueryType {
    PointGet,
    RangeScan,
    NaturalLanguage,
    SemanticSearch,
}

pub struct QueryConstraints {
    pub max_latency_ms: u64,
    pub max_cost: f64,
    pub prefer_accuracy: bool,
}
```

**Return Value**:
```rust
pub enum QueryResponse {
    PassThrough,  // No optimization, execute as-is
    Optimize(QueryPlan),  // Suggest optimized plan
    Intercept(QueryResult),  // Return cached/pre-computed result
}
```

**Typical Use Cases**:
- Natural language to structured query translation
- Semantic search optimization using cartridges
- Query rewriting for performance
- Result caching

**Execution Model**:
- Synchronous (blocking, but timeout enforced)
- Timeout enforced (default: 500ms)
- First response wins (plugins race to optimize)

### 4. Schedule Hook (on_schedule)

Called periodically for maintenance tasks.

**Event Data**:
```rust
pub struct ScheduleEvent {
    pub schedule_id: String,
    pub interval: Duration,
    pub maintenance_window: TimeWindow,
    pub resource_limits: ResourceLimits,
}

pub struct TimeWindow {
    pub start:chrono::DateTime<chrono::Utc>,
    pub end:chrono::DateTime<chrono::Utc>,
}

pub struct ResourceLimits {
    pub max_memory_bytes: u64,
    pub max_cpu_percent: f64,
    pub max_duration: Duration,
}
```

**Typical Use Cases**:
- Build/update structured memory cartridges
- Analyze usage patterns and recommend optimizations
- Performance regression detection
- Index maintenance

**Execution Model**:
- Asynchronous (background task)
- Resource limits enforced
- Tracked by observability system

### 5. Shutdown (on_shutdown)

Called during database graceful shutdown.

**Responsibilities**:
- Flush any pending updates
- Close external connections
- Release allocated resources
- Save plugin state if needed

**Error Handling**:
- Best-effort cleanup
- Force terminate after timeout (default: 10s)
- Database shutdown continues even if plugin cleanup fails

## Hook System

### Hook Types

```rust
pub enum HookType {
    OnInit,
    OnCommit,
    OnQuery,
    OnSchedule,
    OnShutdown,
}

pub struct HookRegistration {
    pub plugin_name: String,
    pub hook_type: HookType,
    pub priority: i32,  // Higher priority executes first
    pub enabled: bool,
}
```

### Priority Execution

Plugins register hooks with priorities. Hooks execute in priority order (high to low).

**Example Priorities**:
- Entity extraction: 100 (run early)
- Query optimization: 50 (run mid)
- Usage analysis: 10 (run late)

**Query Hook Special Case**:
- First non-PassThrough response wins
- Higher priority plugins get first chance
- If all pass through, execute original query

### Hook Error Isolation

```rust
pub struct HookError {
    pub plugin_name: String,
    pub hook_type: HookType,
    pub error: PluginError,
    pub timestamp: i64,
}

pub enum PluginError {
    InitializationFailed(String),
    ExecutionFailed(String),
    Timeout(Duration),
    ResourceExhausted(String),
    ExternalServiceUnavailable(String),
}
```

**Error Handling Strategy**:
1. Log error with plugin name and hook type
2. Increment plugin error counter
3. Disable plugin if error rate > threshold (default: 5 errors in 1 minute)
4. Continue executing other plugins
5. Emit error event for observability

## Plugin Development

### Plugin Trait

```rust
pub trait Plugin: Send + Sync {
    /// Plugin metadata
    fn name(&self) -> &str;
    fn version(&self) -> &str;
    fn dependencies(&self) -> &[&str] {
        &[]
    }

    /// Lifecycle hooks
    async fn on_init(&mut self, context: &PluginContext) -> Result<()>;
    async fn on_commit(&mut self, event: &CommitEvent) -> Result<()>;
    async fn on_query(&mut self, event: &QueryEvent) -> Result<QueryResponse>;
    async fn on_schedule(&mut self, event: &ScheduleEvent) -> Result<()>;
    async fn on_shutdown(&mut self) -> Result<()>;
}
```

### Plugin Context

```rust
pub struct PluginContext {
    pub db_config: DbConfig,

    pub event_system: EventSystemHandle,
    pub resource_quota: ResourceQuota,
```

### Example Plugin

```rust
pub struct EntityExtractorPlugin {
    name: String,
    version: String,
    llm_client: LlmClient,
    config: EntityExtractorConfig,
}

impl Plugin for EntityExtractorPlugin {
    fn name(&self) -> &str {
        &self.name
    }

    fn version(&self) -> &str {
        &self.version
    }

    async fn on_init(&mut self, context: &PluginContext) -> Result<()> {
        // Parse plugin config
        self.config = serde_json::from_value(context.plugin_config.clone())?;

        // Initialize LLM client
        self.llm_client = LlmClient::new(&self.config.llm_provider).await?;

        tracing::info!("EntityExtractor plugin initialized");
        Ok(())
    }

    async fn on_commit(&mut self, event: &CommitEvent) -> Result<()> {
        // Skip if no mutations
        if event.mutations.is_empty() {
            return Ok(());
        }

        // Call LLM to extract entities
        let extraction = self.llm_client
            .extract_entities(&event.mutations)
            .await?;

        // Update entity cartridge
        self.update_cartridge(extraction).await?;

        Ok(())
    }

    async fn on_query(&mut self, _event: &QueryEvent) -> Result<QueryResponse> {
        // This plugin doesn't optimize queries
        Ok(QueryResponse::PassThrough)
    }

    async fn on_schedule(&mut self, _event: &ScheduleEvent) -> Result<()> {
        // This plugin doesn't do scheduled tasks
        Ok(())
    }

    async fn on_shutdown(&mut self) -> Result<()> {
        self.llm_client.close().await?;
        tracing::info!("EntityExtractor plugin shutdown");
        Ok(())
    }
}
```

## Error Handling and Fallbacks

### Error Hierarchy

```rust
pub enum PluginSystemError {
    // Registration errors
    PluginAlreadyRegistered(String),
    PluginNotFound(String),
    InvalidPluginConfiguration(String),

    // Execution errors
    HookExecutionFailed {
        plugin_name: String,
        hook_type: HookType,
        error: String,
    },
    HookTimeout {
        plugin_name: String,
        hook_type: HookType,
        timeout: Duration,
    },

    // Resource errors
    ResourceQuotaExceeded {
        plugin_name: String,
        resource: String,
        usage: u64,
        limit: u64,
    },

    // Initialization errors
    PluginInitializationFailed {
        plugin_name: String,
        error: String,
    },
}
```

### Fallback Strategies

1. **On Commit Hook Failure**:
   - Log error
   - Continue transaction (commit already succeeded)
   - Disable plugin if error rate high

2. **On Query Hook Failure**:
   - Fallback to PassThrough
   - Execute query as-is
   - Log error for debugging

3. **On Schedule Hook Failure**:
   - Skip scheduled task
   - Retry on next schedule
   - Log error

4. **Plugin Initialization Failure**:
   - Plugin not registered
   - Database continues without plugin
   - Error emitted to event system

## Performance Requirements

### Latency Requirements

- **on_init**: <5s
- **on_commit**: <5s (async, non-blocking)
- **on_query**: <500ms (synchronous, blocking)
- **on_schedule**: <60s (async, background)
- **on_shutdown**: <10s (async, best-effort)

### Resource Limits

- **Max memory per plugin**: 100MB
- **Max CPU per plugin**: 10% of system
- **Max concurrent operations**: 5 per plugin
- **Max plugins total**: 10

### Throughput Requirements

- **Commit hooks**: Support 1000+ commits/second
- **Query hooks**: Support 10000+ queries/second
- **Schedule hooks**: Support 10+ concurrent scheduled tasks

## Security Considerations

### Input Validation

- All plugin configurations validated
- Event payloads sanitized
- SQL injection prevention for query hooks

### Access Control

- Plugins run with database privileges

- File system access limited to database directory

### Audit Logging

- All plugin executions logged
